How to read it

Layers flow left to right

Every view is the same six lanes. A domain only shows the lanes it uses.

LaneWhat is in it
BRONZE Raw Ed-Fi API JSON, one node per endpoint. Bronze is fully represented in Silver, so it is drawn as a single JSON node per entity.
SILVER Flattened API resources, per district (silversd<N> schemas; district_sd1 shown as canonical). Parent tables end _p0, children _c1, grandchildren _c2.
GOLD conf gold.* conformed tables. Loaded from goldstage.staging_*, which is column-identical (SCD2 merge), so staging and conf are drawn as one node.
GOLD star Derived dims and facts — dim_student, fact_student_enrollment, and the rest of the star schema.
TEMP Redshift temp / staging tables used mid-flight.
PLATINUM Curated marts — MiRead, EWIMS, rosters, curated_* extracts.

Each view is bounded, exactly as each .drawio file is. A trace stops at the edge of the domain you are looking at: gold.dim_student.student_key traced inside 01 · Student shows no downstream, because its consumers (fact_student_enrollment, the marts) are drawn in their own views. Open the consuming domain and trace from there. Upstream traces do cross the bronze boundary — a silver column steps through its table's dashed bronze edge to reach the API resource.

Dashed, faded table cards are references owned by another view (for example dim_student appearing inside the discipline mart). Only the referenced columns are listed on them — open that table's own domain to see it in full.

How the lineage was derived

goldstage → gold conf → derived → platinum is parsed from the actual ETL SQL (etl/edfi_gold_platinum/sql/**) and manifests with sqlglot, at column level, including the UPDATE-based enrichment passes (dim_student_2..16.sql and friends).

silver → goldstage is reconstructed, not parsed. The authoritative column-mapping JSON lives only in S3 (bronze/silver_to_gold_mapping/), not in the repo. Conf columns are matched to silver columns by stripped name within an entity family.

Match confidence is shown on every conf table. Across the 81 conf tables, 67 matched every column (1.00), 13 scored 0.90–0.99, and 1 scored 0.80–0.89. None fell below 0.80. Unmatched columns are generally derived (surrogate keys, audit columns) rather than missing — but treat a sub-1.00 table as indicative rather than authoritative until the S3 mapping is checked.

platinum.curated_ewims_student_early_warn_incidents_actions is built by PySpark (core/ewims_curated.py), not SQL, so it carries table-level edges only.

Two tables are named for the opposite of what they hold

fact_student_section_enrollment_conf holds attendance events. It actually contains edfi_studentSectionAttendanceEvent rows — its INSERT column list is attendanceeventcategorydescriptor, eventdate, arrivaltime, departuretime and so on, with no enrollment columns at all. It is placed in 12 · Attendance.

fact_student_section_grade_conf holds section enrollments. It actually contains edfi_studentSectionAssociation rows — begindate, enddate, attemptstatusdescriptor, homeroomindicator — and no grade columns whatsoever. Real grades live in fact_grade_conf. It is placed in 07 · Courses & Sections.

The repo knows: fact_student_enrollment.sql aliases the ..._grade_conf table as enr and the ..._enrollment_conf table as enr_att. The derived-layer logic is correct today — this is a comprehension and maintenance hazard, not a live data bug. Both views place these tables by their contents, not their names.
