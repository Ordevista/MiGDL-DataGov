The MiGDL pipeline,
read as an ontology.

MiGDL moves Michigan school data through four medallion layers, from raw Ed-Fi JSON to the curated products four applications read. This page is generated from the pipeline's own ETL SQL — every table, every column, and every derivation parsed out of etl/edfi_gold_platinum/sql and its manifests, then crosswalked back to the Ed-Fi resources it started from. Nothing here is hand-transcribed.

The one idea

Renaming is not
transforming

The pipeline has two kinds of hop, and they behave nothing alike. The first is conforming: an Ed-Fi resource is flattened into Silver, landed in goldstage, and merged into a Gold conformed table. Column for column, it is the same data wearing underscores. The second is deriving: conformed tables are joined, descriptors are split, keys are minted, and something genuinely new appears. Reading the whole pipeline as one undifferentiated flow is what makes lineage feel impenetrable.

The two rows are drawn at the same scale because they cost roughly the same to run — but they carry completely different risk. A conforming hop can be verified by comparing column lists. A deriving hop can only be verified by reading the SQL, which is why the derived layer is where this pipeline's known defects have lived.

Why this matters for governance. Column-level lineage across a conforming hop is recoverable by name-matching alone. Across a deriving hop it is not — it has to be parsed out of the SQL, because a single output column may draw on four inputs and a thirty-branch CASE. The crosswalk further down carries a confidence score for exactly this reason: the Silver-to-Gold mapping is reconstructed, while everything downstream of it is read.

Worked example

Following one grade level
through five layers

A student's entry grade level starts as a single Ed-Fi descriptor string and ends as two Gold columns. Watch where it changes: nothing happens to it until the fourth step, and then everything happens at once.

Steps one through three are the conforming hop — the value is carried, not read. Step four is the deriving hop: SPLIT_PART(descriptor, '#', 2) strips the Ed-Fi namespace, then a thirty-branch CASE folds Michigan's grade vocabulary ('pre k', 'PK', 'preschool/prekindergarten', '16') into one label. Step five runs the same logic again to emit a sortable integer, using negatives for pre-kindergarten so ordering survives.

The crosswalk

Every resource this pipeline pulls, traced to the Gold conformed table that holds it. Sixty-three are core Ed-Fi; eighteen are Michigan extensions under the /MI/ namespace, almost all of them the Education Entity Master. The bar is the share of the conformed table's columns that could be matched back to a Silver column by name.

What is verified and what is classified. The resource list, API paths and /MI/ namespaces are read from configs/endpoints.json. The Ed-Fi 4.0 domain column is a manual classification against the Unifying Data Model and should be checked against Alliance documentation before anyone treats it as authoritative — a few are genuinely arguable, studentSectionAssociations most of all.

Where the names lie

Two tables named for
the opposite of their contents

Both are still in stg. The derived layer already compensates for them, so this is a comprehension hazard rather than a live data bug — but it has bitten once already, and the repo says so in its own comments.

It caused a real defect. fact_student_section_enrollment.sql carries the line “Changed from fact_student_section_enrollment_conf (attendance events) to ensure all enrolled students appear regardless of whether attendance was recorded”. Enrollment had been sourced from the attendance table, which silently dropped every student with no attendance recorded. Note the compensating aliases still in the SQL: the table named ..._grade_conf is aliased enr, and ..._enrollment_conf is aliased enr_att.

The names originate outside this repo — in the column-mapping JSON in S3 (bronze/silver_to_gold_mapping/) — so a rename has to move that config, the goldstage datasets, the manifest and all downstream SQL together.

Of the Gold and Platinum tables in this pipeline, the API reads . The conformed layer is almost entirely absent from it: the endpoints are served by the star schema and the curated marts.

Unreachable here does not mean unused. This is one consumer. Anything else that reads Redshift directly — Amorphic, analyst queries, dashboards, a second API — is invisible to this count. What it does show is that nothing an app sees passes through those 97 tables, so a change there cannot reach an app except through the derived and curated tables that do.

The landing zone

What lands in Bronze,
and what moves on

Bronze is one flat table per Ed-Fi resource, every column a varchar — read here from an Athena information_schema export rather than inferred. It holds 403 tables and 10,329 columns. The pipeline ingests 81 of those tables. The other 322 are never promoted to Silver, and 317 of them are descriptors — Ed-Fi's controlled vocabularies, landed but unused.

Every one of the 1,663 real Silver parent columns resolves to a Bronze column, so the Bronze-to-Silver hop is read rather than reconstructed — unlike Silver-to-Gold, whose mapping config lives in S3. What does not survive the hop is uniform: the same ten columns are dropped from every one of the 81 resources.

The dropped ten are change-capture metadata, not payload. changeversion, keyvalues, oldkeyvalues, newkeyvalues, recordflag, typeofdata, edfiversion, datastandard, upload_date, and schooldistrictid (Silver carries schooldistrict instead). Nothing downstream needs them today — but changeversion and the keyvalue triplet are Ed-Fi's own change-tracking fields, so an incremental-sync design would have to read Bronze directly to get them.

Only the 81 ingested tables are drawn in the map above. The other 322 connect to nothing, and adding 322 unconnected dots would cost the graph its readability for no gain. They are all listed here instead.
