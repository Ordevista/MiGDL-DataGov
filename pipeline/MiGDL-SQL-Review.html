What was checked

11 checks, and
what each one means

Four are ranked high because each has a known failure mode in this codebase. The two marked informational are listed for confirmation rather than asserted as defects — they have a high legitimate-hit rate and saying otherwise would waste review time.

The neutralised-LEFT-JOIN check flags 6 statements (7 joins). A WHERE predicate on the outer table silently converts a LEFT JOIN into an INNER JOIN and drops rows. Most of these are in the consumption API, where they gate the caller's student filter on state_student_id — see the section below.

An earlier run of this audit reported zero. That run capped analysis at the first six SELECT scopes per statement, so predicates in the deepest CTEs were never examined; the cap is gone. The detector was self-tested against four synthetic cases (two positive, two negative).

The second corpus

The API is in here too

19 queries from maisa-consumption-api — one per REST endpoint — measured by the same 11 checks. They are tagged API in the lists below, and either corpus can be filtered out.

These queries are not read from the source as text: each handler's query builder is executed with a synthetic request, so what is analysed is the statement the Lambda actually issues, with its filter fragments assembled — including through import aliases, so /miread/district/assessment is read from district_assessment_v2.py, which is what the handler actually imports. The literals you will see in the API rows below — '19', '2025', 'S1' — are that synthetic request's parameters, not production values; they mark where a caller's arguments land. The API reads 23 gold and platinum tables across 19 endpoints, with only 12 joins in total — the medallion layers are wide enough that most endpoints select from a single table.

Five of the API's 12 joins are neutralised LEFT JOINs, and they share one shape. /app/student/attendance, /contacts, /enrollment, /sectionenrollment and /sectiongrades each LEFT JOIN gold.dim_student, then filter ds.state_student_id IN (...) in the WHERE clause when the caller passes student_id.

That turns the LEFT JOIN into an INNER JOIN, so a student with no matching dim_student row — or no state ID yet — returns nothing from those five endpoints. This is the identifier problem from the Identifier Strategy ADR surfacing in the delivery layer: the state UIC arrives late or never, and these endpoints key the caller's student filter on it.

To verify: call one of the five with a student_id for a student whose dim_student row is missing or whose state_student_id is null, and compare against the same query with the predicate moved into the ON clause.

Vocabulary

Where one term
means two things

Not a style review. Every Gold and Platinum column is traced to the Silver column it ultimately comes from, then names and sources are compared against each other. Three things fall out, and all three are checkable claims rather than opinions.

One name, different meanings 12

The same column name resolves to materially different sources in different tables. The identity ones matter most: student_unique_id is the district-local studentuniqueid in gold.dim_student_conf, but the state identificationcode in platinum.fact_miread_student_context. Same name, different person-identifier. district_student_id and district_staff_id have the same split, and race_ethnicity_detail is ancestryethnicorigindescriptor for a student but raceorderchoicedescriptor for a staff member.

One source, contradictory names 3

The reverse. identificationcode is carried downstream as both district_student_id and state_student_id — both cannot be right. srcschoolyear becomes both start_date and end_date. Only groups whose names contradict on scope (district / state / local) or on which end of a range they name are listed; a descriptor fanning out into several booleans is normal design and is deliberately not flagged.

Two spellings, both in use 1

school_year and schoolyear are both columns of 15 Gold tables, holding the same value. The derived SQL renames schoolyear to school_year in an inner query and back to schoolyear in the outer one, and both land in the target — you can read it in dim_student.sql at lines 86 and 55. They agree today. Nothing keeps them agreeing, and a join against the wrong one stays invisible until they drift.

These are listed with the other findings below, tagged SCHEMA, with ids beginning NAME-. They are schema-wide rather than tied to one statement, so their copy blocks carry the evidence — the tables and the sources — instead of a file and line.
